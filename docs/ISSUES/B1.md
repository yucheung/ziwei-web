## Issue B1-1：排盤規則面板（Rule Info Panel）

**目標**：讓使用者/開發者可驗證命盤正確性 — 顯示影響排盤的所有設置與版本。

**需求**：
- 在 ChartGrid **上方**（醒目、隨時可見）新增唯讀規則資訊區，顯示：
  - 流派：三合派（`school: "sanhe"`，ruleVersion `sanhe-v1`）
  - 年界設定：`normal` / `exact`（對應 Settings.yearBoundary）
  - 節氣 / 閏月處理：說明依 iztro 規則
  - 時區：Asia/Taipei（+8），顯示目前 UTC offset
  - 真太陽時：啟用與否 + 出生地經度（longitude，預設 121.56）
  - 晚子時處理：`current` / `forward`
  - iztro 版本：`^2.5.8`（防讀 package.json，直接硬編碼或設常數）

**關鍵**：此面板**只顯示真實用於排盤的參數**，不新增不在實際排盤流程使用的假欄位。欄位資料源必須與 InputForm 送出的 setChartInput 完全一致。

**驗收測試**：
- 組件測試：給定一份 chart input（含真太陽時 + 經度 + 年界 + 晚子時），面板渲染出對應的參數值
- 測試：面板文字全部走 `t()`（zh-TW / zh-CN 雙語）
- 手動：變更 Settings（星系 / 年界 / 晚子時）後面板同步更新

**不得**：不重構 ChartsGrid、不移動 DOM、不改變排盤計算邏輯。

## Issue B1-2：完整命盤 JSON 匯出（確定性快照）

**目標**：**相同輸入 → 相同 JSON**（確定性），含設定 + 結果 + 盤五層 + 版本。

**需求**：
- 在既有匯出區新增「匯出命盤 JSON」按鈕（export.ts 內新函式 `generateChartJson`）
- JSON 結構（確定性、順序固定）：
  ```json
  {
    "schemaVersion": "zhChart-v1",
    "settings": { "school": "sanhe", "yearBoundary": "exact",
                  "trueSolarTime": {"enabled":true,"longitude":121.56},
                  "lateZiHandling":"current", "iztroVersion":"2.5.8" },
    "input": { "solarDate": "...", "gender": "...", "birthplaceLongitude": 121.56 },
    "chart": { "palaces": [...], "fiveElementsClass": "...", "soulStar": "...",
               "bodyStar": "...", "heavenlyStem": "...", "earthlyBranch": "..." },
    "horoscope": { "decadal": [...], "yearly": [...], "monthly": [...],
                   "daily": [...], "hourly": [...] },
    "determinism": true
  }
  ```
- **不含 `generatedAt` 時間戳**（使用者確認）— 保證同一輸入兩次輸出 byte 相等。若要紀錄產生時間，放外部 metadata 而非命盤 JSON。

**驗收測試**：
- **確定性**：同一 input 呼叫兩次 `generateChartJson` → `JSON.stringify` 結果完全相等（deepEqual）
- **schema**：含全部頂層欄位（settings/chart/horoscope/version）
- **雙語**：星曜/宮位 key 用 canonical key，輸出含 locale 對應
- 下載：可 Blob 下載 .json 檔

**不（過度）**：不引入版本序列化依賴；在此不做「匯出合併移除」功能。

## Issue B1-3：LLM 輸入檢視（Debug 面板）

**目標**：使用者可看到實際送給模型的 **provider / model / promptVersion / ruleVersion / 摘要與 prompt**（B1 橫向 LLM 記錄）。

**需求**：
- ReadingPanel 新增可摺疊「檢視 LLM 輸入」區：
  - provider / model
  - promptVersion（來自 constants）
  - `systemPrompt` + `userPrompt` 全文（即 `buildReadingPrompt` 與 `sanitizeUserInput` 的真實輸出）
  - ruleSetVersion（現 `sanhe-v1`）
  - 摘要長度（字元/詞）
- 此區為**唯讀**、僅顯示，不影響既有串流。

**B1 橫向任務**：記錄 provider/model/promptVersion/ruleSetVersion/usage/latency/status 到可查資料結構（暫 localStorage，B5 前不接規則庫）。

**驗收測試**：
- ReadingPanel 測試：給 fixed chart + llmConfig → Debug 面板顯示的 prompt 與 `buildReadingPrompt(...)` 輸出逐字相等
- 無 apiKey 時，檢視面板仍可顯示（唯讀不受授權影響）

## Issue B1-4：排盤 Golden 測試框架（排盤 Golden 子集）

**目標**：建立**可執行**的排盤 Golden 框架，首批 fixtures 覆蓋排盤關鍵邊界。

**需求**：
- 建 `src/__tests__/golden/` 目錄與測試框架（`排盤Golden.spec.ts`）
- **只做「排盤 Golden」**：驗證 iztro 排盤輸出（命宮/主星/四化/運限）vs **人工核算 / 權威來源**的預期值
- fixtures **至少 10 組**，含：
  - 子時 / 晚子時（B5 夜子時）
  - 立春 / 農曆年界附近
  - 閏月
  - 真太陽時造成時辰變更（longitude 影響）
  - 男女順逆行
  - 空宮
  - 大限切換邊界
  - 常見四化（生年祿權科忌）落宮
- **expected 值採分級來源**（使用者確認）：
  - **Level 1（實作者建立）**：實作者（claude worker）依 iztro 規則 / 文件推導的預期值 — 主力，可作開工
  - **Level 2（權威案例）**：使用者提供的權威案例（書籍案例、其他工具輸出）— **作為加強錨點，非開工前置條件**
  - fixture 註記 `sourceLevel: "L1" | "L2"` 與來源說明
- **僅做「排盤事實相等」斷言**（如：某日時 → 命宮對象、某主星落某宮、真太陽時後時辰改變）
- **不做**規則 Golden（格局成立）、**不做**解讀案例集（LLM 推論）

> 注意 D3：「**自己的命盤不能單獨證明排盤正確**」，需用權威來源或跨工具一致的結果當 expected。分級來源設計即為此：L1 實作者建立（開工主力），L2 權威錨（上線前補強）。

**驗收測試**：`npm run test golden` 全綠；每組 fixture 有來源註記；覆盤 ≥10 組
