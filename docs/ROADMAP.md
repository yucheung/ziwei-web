### iztro 提供 vs 不提供的資料

**iztro 已提供**（資料層完備）：
- 12 宮：name, majorStars, heavenlyStem, earthlyBranch, changsheng12, boshi12
- 運限五層：decadal/yearly/monthly/daily/hourly，各含 stars[], mutagen, heavenlyStem, palaceNames
- 命主、身主、命宮、身宮
- 五行局、性別
- 四化（祿權科忌）
- 生年四化、大限四化、流年四化

**iztro 不提供**（需自建）：
- ❌ 格局判定（grep iztro lib 無 pattern/格局相關 export）
- ❌ 三方四正關係計算（需自建 palace relationship 層）
- ❌ 星曜解釋規則
- ❌ 宮位主題解讀
- ❌ 運限推論邏輯
- ❌ 合盤規則
- ❌ 任何命理知識庫

### 核心缺口

> **現有系統是「排盤機」+「LLM 祈禱機」。**
> iztro 產出完整盤面資料，但 prompts.ts 只把摘要文字塞進 prompt，
> 沒有結構化的命理規則層。LLM 靠自己的訓練知識解讀，品質不可控。

## 三、技術架構提案

### 現有管線

```
iztro 排盤 → summarizeAstrolabe() → 純文字摘要 → buildReadingPrompt() → LLM → 結果
```

問題：摘要文字無結構、無規則、無證據追溯。

### 目標管線

```
iztro 排盤
  ↓
ChartAnalyzer（結構化分析層）← 知識庫（JSON rules / 規則引擎）
  ↓
StructuredSummary（盤面事實 + 規則命中 + 推論鏈）← 證據追溯
  ↓
buildReadingPrompt()（帶結構化摘要 + 規則引用）→ LLM → 結果
  ↓
CitationTracer（驗證：LLM 輸出是否引用了結構化摘要中的事實）
```

### 知識庫格式選型（需討論）

| 方案 | 優點 | 缺點 | 適合層次 |
|---|---|---|---|
| **A. JSON Rule Engine** | 確定性、可測試、無 token 成本 | 規則維護成本高、組合爆炸 | 1-6（格局、四化） |
| **B. Vector RAG** | 靈活、可容模糊推理 | 不確定性、token 成本、需 embedding | 7-10（專題、合盤） |
| **C. Prompt-only** | 最快實現 | 品質不可控、無可測試性 | 1（緊急可用） |
| **D. 混合（A+B）** | 各取所長 | 架構複雜度高 | 整體最優 |

**初步建議**：第 1-6 層用 JSON Rule Engine（確定性判斷），第 7-12 層用 Vector RAG（模糊推理）。但這需要討論。

## 四、分期實施計畫

### Phase 0：排盤透明化（P0 最高優先）

**目標**：讓使用者（和開發者）能驗證命盤正確性。

| 項目 | 內容 | 工作量 | 依賴 |
|---|---|---|---|
| 排盤規則面板 | 顯示：流派、年界、節氣、閏月、時區、真太陽時設定、iztro 版本 | 小 | 無 |
| 完整命盤 JSON 匯出 | 包含設定 + 計算結果 + 運限 + 版本 | 小 | 無 |
| 命理回歸測試框架 | 固定生辰案例庫 → 自動驗證命宮/主星/四化/大限 | 中 | 需 5-10 個參考命盤 |
| LLM 輸入檢視 | ReadingPanel 顯示實際送給模型的摘要 + prompt | 小 | 無 |

### Phase 1：結構化分析層（核心）

**目標**：建立 iztro 資料 → 結構化摘要的管線。

| 項目 | 內容 | 工作量 | 依賴 |
|---|---|---|---|
| ChartAnalyzer | 將 astrolabe 轉為結構化 JSON（宮位事實 + 星曜屬性 + 三方四正 + 四化落宮）| **大** | 無 |
| 三方四正計算 | 自建 palace relationship 層（4×4 環狀空間的三方四正映射）| 中 | 無 |
| 星曜知識庫 v1 | 十四主星 + 六吉六煞：基本性質、廟旺利陷、宮位含義（JSON 格式）| 中 | 無 |
| summarizeAstrolabe 重構 | 從純文字升級為結構化 JSON（保留 backward compat）| 中 | ChartAnalyzer |
| 解讀證據追溯 | StructuredSummary 帶 rule citations，LLM 輸出可回溯 | 中 | ChartAnalyzer |

### Phase 2：規則引擎

**目標**：將命理判斷從 LLM 自由推理升級為規則驅動。

| 項目 | 內容 | 工作量 | 依賴 |
|---|---|---|---|
| 四化規則庫 v1 | 生年四化基本規則（祿權科忌在各宮的含義）| 中 | Phase 1 |
| 格式規則庫 v1 | 10 個常見格局的判定條件 | 中 | Phase 1 |
| 宮位主題知識 v1 | 命宮/財宮/官祿宮/夫妻宮的核心解讀框架 | 中 | Phase 1 |
| 運限推論 v1 | 大限背景 + 流年觸發的基本推論鏈 | 大 | Phase 1 + 四化 |
| 命理回歸測試 v2 | 擴充至 20+ 案例，覆蓋格局/四化/運限 | 中 | Phase 1-2 |

### Phase 3：進階功能

**目標**：學習與日常使用功能。

| 項目 | 內容 | 工作量 | 依賴 |
|---|---|---|---|
| 多命盤收藏 | localStorage 存多個命盤（姓名+生辰+標籤）| 中 | 無 |
| URL 分享 | hash 參數加密命盤設定，一鍵分享 | 中 | 無 |
| 解讀歷史 | 同一命盤不同日期/問題的解讀保存 | 中 | 無 |
| 對話式追問 | 固定引用當前命盤與運限的多輪對話 | 大 | Phase 1 |
| 列印模式 | CSS print，命盤+解讀 A4 排版 | 小 | 無 |

### Phase 4：合盤與專題

**目標**：合盤規則化 + 專題深度解讀。

| 項目 | 內容 | 工作量 | 依賴 |
|---|---|---|---|
| 合盤規則庫 | 雙方本命互動、運限同步、關係模型 | 大 | Phase 1-2 |
| 專題解讀 | 性格/財運/感情/健康等分項規則 | 大 | Phase 1-2 |
| 八字知識庫 | 十神、藏干、格局、喜忌 | 大 | 獨立 |
| 紫微八字交叉驗證 | 兩套體系結論的交叉參照 | 大 | 兩者各自完成 |
| 流年走勢圖 | 運限分數曲線化（依賴規則公開後的分數）| 中 | Phase 2 |

### Phase 5：大眾化（P2）

**目標**：走向一般大眾服務。

| 項目 | 內容 |
|---|---|
| 帳號系統 | 跨裝置同步、資料刪除/下載 |
| 匿名化分享 | 非 URL 加密，而是真正的匿名命盤庫 |
| LLM 成本控制 | 額度管理、失敗重試 |
| 敏感議題提示 | 健康/財務/婚姻/生死的斷言邊界 |
| 新手引導 | 範例命盤 + 教學模式 |

## 五、討論點與不確定性

### 🔴 需要你決定的

**D1. 流派策略**
> 現有 prompts 寫「兼通三合派與飛星派」，但兩派四化表差異大。
> - 選項 A：只做三合派（最常用），飛星派標「不保證」
> - 選項 B：兩派都做，四化表可切換
> - 選項 C：先三合，飛星留 TODO
>
> **建議**：選 C。三合派是主流，飛星派規則更複雜。

**D2. 知識庫格式**
> 12 層知識怎麼存？（見上方「技術架構提案」）
> - JSON Rule Engine（確定性）vs Vector RAG（靈活性）vs 混合
>
> **建議**：Phase 1-2 先用 JSON（可測試），Phase 3+ 視需求加 RAG。

**D3. 命理回歸測試的 golden set**
> 需要 5-10 個已知正確的參考命盤。來源：
> - 選項 A：古籍案例（如紫微斗數全書的範例）
> - 選項 B：你自己的命盤 + 家人的（已知準確）
> - 選項 C：開源命盤資料集
>
> **建議**：B 為主（最可信），A 為輔（覆蓋特殊格局）。

**D4. 八字的定位**
> 現有 FourPillars 只是顯示。要走到完整解讀是：
> - 選項 A：獨立大工程（11 層知識庫的第 11 層）
> - 選項 B：只做基本顯示 + 簡單 LLM 解讀（不建規則庫）
> - 選項 C：先擱置，專注紫微
>
> **建議**：C。八字與紫微是兩套獨立體系，混在一起會讓系統複雜度暴增。

**D5. 系統定位**
> 這是給自己用的工具還是要給別人用？
> - 自己用：功能深度優先，UX 可以粗糙
> - 給別人用：UX 優先，功能可以漸進
>
> 影響 Phase 5 是否值得做。

### 🟡 需要技術驗證的

**V1. iztro 運限資料深度**
> iztro horoscope() 提供 decadal/yearly/monthly/daily/hourly 的 stars[] 和 mutagen，
> 但「各層四化疊加」的計算是否在 iztro 內完成？還是需要自建？
> → 需要實測：取一個已知生辰，比較 iztro 運限輸出與手算結果。

**V2. 三方四正計算**
> 我們已有 ChartGrid 的 4×4 空間映射（roving tabindex 用的），
> 但「三方四正」的定義是「命宮→財帛宮→官祿宮→遷移宮」的宮位關係，
> 需要確認 iztro 是否已經計算好 palace.threeFour 或需要自建。

**V3. LLM 結構化摘要的 token 效益**
> 把完整 astrolabe JSON（~2KB）塞進 prompt vs 只塞結構化摘要（~500B），
> 哪個 LLM 解讀品質更好？需要 A/B 測試。

**V4. 格局判定的規則化可行性**
> 有些格局（如「紫微在午」）可以規則化，但有些（如「機月同梁」）需要多宮聯動。
> 需要評估：規則化能覆蓋多少比例的常見格局？

### 🟢 已有共識的

- **排盤透明化**（Phase 0）是最高優先，無爭議
- **結構化分析層**（Phase 1）是核心基礎，所有後續功能都依賴它
- **LLM 輸入檢視**是低成本高價值的品質工具
- **命理回歸測試**是一般 E2E 無法替代的
